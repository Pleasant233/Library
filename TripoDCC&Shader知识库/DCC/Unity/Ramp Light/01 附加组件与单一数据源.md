## 一、返工实录：从 Atlas 资产到组件内联

这是本阶段**最值得记的一件事**，先讲结论再讲过程。

### 第一版（阶段 1）：Atlas 资产 + Profile 索引

```text
美术工作流：
1. 右键创建一个 RampLightAtlas 资产
2. 在资产里加若干 Profile（每个 Profile 一条 Gradient）
3. 给灯挂 RampLight 组件
4. 在组件上引用那个 Atlas，再填一个 profileIndex = 3
```

代码规模：`RampLightAtlas`（157 行）+ `RampLightProfile`（57 行）+ `RampLightAtlasBaker`（246 行）+ `RampLightAtlasEditor`（117 行）= **约 580 行**，还包括一套内容哈希、`RGBAHalf` 子资源烘焙、`AssetPostprocessor` 增量重烘的机制。

### 第二版（阶段 1.1）：组件直接存 Gradient

```text
美术工作流：
1. 给灯挂 RampLight 组件
2. 调 Gradient
```

那 580 行**全部删除**。

### 判断依据是什么

不是"代码太多了"，而是三个具体的坏味道：

**1. 美术工作流有一步是纯仪式。** "先去创建一个资产"对美术没有任何意义——他要调的是**这盏灯**的颜色，不是去维护一张全局表。工具的步骤数直接decide它会不会被用。

**2. `profileIndex` 是个脆弱的间接层。** 一个整数指向列表里的第 N 项。**重排 Profile 顺序，所有灯的 Ramp 全部错位**，而且没有任何报错。这类"用序号当引用"的设计在 Unity 里格外危险，因为序列化会把错误的值一直带下去。

**3. 出现了双数据源的苗头。** 组件既可能用 Atlas 的 Profile、又可能有自己的本地值，那"哪个生效"就需要一个模式开关，接着需要回退逻辑，接着需要"两边不一致时怎么办"。**这条路的尽头是一堆兜底代码。**

> [!warning] "GPU 需要一张 Atlas" ≠ "美术需要编辑一张 Atlas"
> 这是当时最核心的认知错误。最终 Shader 采样时**确实**需要一张多行 Atlas 纹理（一行一盏灯），第一版把这个 **GPU 侧的数据布局**直接暴露成了**美术侧的编辑单位**。
>
> 正确的分层是：**美术编辑逐灯 Gradient → 运行时 Bridge 自动把所有灯的采样行拼成共享 Atlas**。美术永远看不到 Atlas 的存在。
>
> 更通用的教训：**别让底层的数据布局渗透到用户的操作模型里。** 你在写工具时会反复遇到这个陷阱。

### 什么被保留了

删掉 Atlas 资产**不等于**放弃 Atlas 架构。共享 Atlas 仍然是 GPU 侧的方案，只是改为阶段 2 由 Runtime Bridge **在内存中自动生成**，行号由 Bridge 按 `Light.GetInstanceID()` 分配，**不序列化到场景或 Prefab**。

> [!note] 行号不落盘，是这个设计的关键
> 如果把行号存进场景，它就变成了第二个 `profileIndex`——同样的错位问题会原地复活。**自动分配的、不持久化的索引**才安全。

## 二、组件本体：三个 Attribute 定义了「附加组件」

```csharp
[ExecuteAlways]
[DisallowMultipleComponent]
[RequireComponent(typeof(Light))]
public sealed class RampLight : MonoBehaviour
```

对熟悉 Unity 的人这三行很常规，但放在"附加组件"这个语境下，每一个都在解决一个具体问题：

| Attribute | 作用 | 为什么这里必须有 |
| --- | --- | --- |
| `RequireComponent(typeof(Light))` | 挂载时自动补 `Light`，且不能单独删 `Light` | Ramp 是对 `Light` 的**增强**，没有宿主就无意义 |
| `DisallowMultipleComponent` | 一个物体只能挂一个 | 两个 Ramp 打同一盏灯，谁生效？直接从类型上排除 |
| `ExecuteAlways` | 编辑模式下也执行生命周期回调 | 美术要在**不进 Play Mode** 的情况下看到效果 |

> [!tip] `ExecuteAlways` 是 TA 工具的默认选项
> 运行时逻辑可以只在 Play Mode 跑，但**创作工具必须在编辑模式活着**。美术不会为了看一眼灯光效果去按播放键。旧的 `[ExecuteInEditMode]` 已被它取代。

### 数据字段

```csharp
[Header("Ramp")]
[SerializeField, GradientUsage(true, ColorSpace.Linear)]
private Gradient _gradient = CreateNeutralGradient();

[Header("Sampling")]
[SerializeField, Range(0.0f, 1.0f)] private float _distanceStart;
[SerializeField, Range(0.0f, 1.0f)] private float _distanceEnd = 1.0f;
[SerializeField, Range(0.0f, 1.0f)] private float _normalInfluence;
[SerializeField, Min(0.0f)] private float _rampIntensity = 1.0f;
```

`GradientUsage(true, ColorSpace.Linear)` 的两个参数都关键，细节见 [[02 Gradient 采样与颜色空间]]：`true` = HDR（允许亮度 > 1，戏剧化打光需要），`Linear` = 线性空间（光照计算的正确空间）。

**默认值 = 白到白的 Gradient + `rampIntensity = 1`**，这不是随手填的：

> [!note] 默认值必须等价于「功能关闭」
> 新挂上组件的瞬间，画面**不应该有任何变化**。白色 Ramp 乘上原光色 = 原光色。
> 这条原则叫 **Feature-off 等价**，它让你随时能用「删掉组件 / 保留组件但用默认值」两种方式对照，快速定位"是我的功能出错，还是本来就这样"。任何要插入现有管线的功能都该先满足这一条。

## 三、私有字段 + 只读属性：为什么不用 public

```csharp
[SerializeField] private float _distanceStart;
public float DistanceStart => _distanceStart;
```

比 `public float distanceStart` 多写一行，换来的是：

- **Inspector 能编、外部代码不能改**。Ramp 数据的唯一写入者是 Inspector（经 `SerializedObject`），后续的 Bridge 只读。
- **不变量有唯一守门人**。`_distanceEnd >= _distanceStart + 0.001` 这类约束只在组件内部维护，不会被外部代码绕过。

> [!warning] 这一版里有个真实的疏漏
> `_gradient` 是唯一**没有**公开只读属性的字段——四个采样参数都有，最核心的 Gradient 没有。当前只有 Editor 通过 `SerializedProperty` 访问，所以不报错；但阶段 2 的 Bridge 要读它，届时必须补。
> 一致性缺口就是这样产生的：**加字段时顺手加访问器，比事后补容易。**

## 四、生命周期：三个入口，没有 Update

```csharp
private void OnEnable()   { ValidateSerializedData(); ValidateAttachedLight(); }
private void OnValidate() { _attachedLight = null; ValidateSerializedData(); ValidateAttachedLight(); }
private void OnDisable()  { _hasLoggedUnsupportedLightWarning = false; }
```

**没有 `Update`，没有 Coroutine，没有场景搜索**——这是硬性约束，不是风格偏好。

```mermaid
flowchart LR
    A["美术改参数"] --> B["OnValidate\n（Unity 自动调用）"]
    B --> C["校验不变量"]
    C --> D["标记预览失效"]
    D --> E["阶段 2：\n通知 Bridge 更新"]

    style E stroke-dasharray: 5 5
```

> [!tip] 事件驱动 vs 轮询：TA 工具的分水岭
> 一个 `Update` 里 `FindObjectsOfType<RampLight>()` 的工具，在 50 盏灯的场景里会**明显拖慢编辑器**，而且美术只会觉得"Unity 卡"，不会想到是你的工具。
> **数据变了才推送**——`OnValidate` / `OnEnable` / `OnDisable` 就是 Unity 给你的推送时机。`OnValidate` 在 Inspector 改动、撤销、反序列化后都会触发，覆盖面比你手写的检测完整。

`OnValidate` 里第一行 `_attachedLight = null` 是清缓存：`Light` 组件可能被换掉，缓存的引用会失效。

### 只支持 Point Light，且只警告一次

```csharp
private bool _hasLoggedUnsupportedLightWarning;   // [NonSerialized]
```

挂到 Spot Light 上时，组件**不自动改灯的类型**（那是擅自修改用户数据），只警告。这个 bool 的作用是防刷屏——`OnValidate` 可能被高频触发，没有它 Console 会被淹掉。`OnDisable` 里重置，保证下次启用还能提醒一次。

> [!note] 「不自动修正用户数据」是条底线
> 检测到不支持的配置时，**提示** > **自动改**。自动改会让用户困惑"我明明设的是 Spot，怎么变 Point 了"，而且丢失了他原本的意图。

## 五、下一步

组件存了一条 `Gradient`，但 GPU 要的是纹理像素。中间的转换有一套必须**编辑器和 Shader 完全一致**的约定——[[02 Gradient 采样与颜色空间]] 讲这件事，包括一个"预览串色"的排查过程。

## 速记

- **返工的核心教训：GPU 的数据布局 ≠ 美术的编辑单位。** 共享 Atlas 该由运行时自动生成，不该让美术手工创建。
- 删掉 580 行的三个依据：**工作流有仪式步骤**、**用序号当引用（重排即错位）**、**双数据源必然带来兜底代码**。
- 自动分配、**不序列化**的行号才安全；一旦落盘就是第二个 `profileIndex`。
- 附加组件三件套：`RequireComponent`（宿主）+ `DisallowMultipleComponent`（唯一）+ `ExecuteAlways`（编辑模式可见）。
- **默认值必须 Feature-off 等价**（白 Ramp = 原光色），这是随时能对照排错的前提。
- `[SerializeField] private` + 只读属性：Inspector 可编、外部只读、不变量有唯一守门人。
- **事件驱动（`OnValidate`/`OnEnable`/`OnDisable`），绝不轮询**；重复警告要用 `[NonSerialized]` 标志位节流。
- 检测到不支持的配置：**提示，不自动改用户数据**。
